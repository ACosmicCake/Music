# Notes for agents

The app is in `world-woodshed/`, a Vite project with plain JavaScript ES modules and no framework. It is an installable PWA (vite-plugin-pwa) deployed to GitHub Pages by `.github/workflows/deploy.yml`.

Run `npm install` then `npm run dev` (or `npm run build && npm run preview` to test the service worker) inside `world-woodshed/`, and drive it with Playwright to check a change. `npm test` (Vitest, `test/`) covers state migration and device merging (`src/sync.js`), chord parsing and diatonic harmony (`theory.test.js`), the skill model and backups (`engine.test.js`), the memory model and session planner (`curriculum.test.js`), playing to notation and the MusicXML/MIDI files (`notate.test.js`), routine time fitting (`routines.test.js`), practice statistics (`stats.test.js`), the time-stretch (`stretch.test.js`), your own tunes (`mytunes.test.js`), the Library (`library.test.js`, `libsync.test.js`, `midiread.test.js`), the reading library (`readlib.test.js`), count grids (`countgrid.test.js`), score recognition and its MusicXML (`omr.test.js`) and Roman numerals for the jazz standards (`harmony.test.js`), and checks the content data (rhythm lengths, chord symbols, drill bars, reading generators). `npm run lint` runs ESLint (`eslint.config.js`: `eslint:recommended`, with unused names as warnings); both workflows run lint and tests before building. Tests that load `engine.js` import `test/env.js` first (an in-memory `localStorage` and a stub `document`) and pin the clock with `vi.setSystemTime`.

## Files

`src/main.js` imports everything in order and boots the app:

- `index.html`: page shell only.
- `src/styles.css`: all CSS (design tokens on `:root`, dark mode via `prefers-color-scheme` and `data-theme`). Fonts are bundled from `@fontsource` so the app works offline. A compact layout for small phones (3-inch screens such as the Unihertz Jelly Star) lives under `html.compact`, set by `applyDisplay()` in `src/ui/core.js`: automatic below 380 × 640 CSS px or chosen in Settings → Display, with a text size (`html[data-text]`); both are per device (`DEVICE_SETTINGS`). Check new UI at 240 px wide as well as on a normal phone.
- `src/data.js`: content. Intervals and anchor songs, chords, progressions, world scales and ragas/maqamat, rhythm cycles, tunes, grooves, technique exercises, styles (atlas regions). It merges in `src/content/`.
- `src/content/`: long-form content. `styles-a.js`, `styles-b.js` (deep-dive fields for the original regions: history, sub-styles, how it works, listening path, players, study, practice) and `styles-new.js` (eight whole new styles); `lessons.js` (the theory course); `rhythms-new.js` (more rhythms per style, appended to `RHYTHMS`) and `rhythms-var.js` (variations, fills, cycles, tempo range and tips for every rhythm, attached as `r.var`; the player's own part never changes in a variation); `drills-a.js`, `drills-b.js` (four style drills per style, `D.DRILLS`); `exercise-vars.js` (variations, speed burst and listening cue per technique exercise, `ex.vars`); `gym.js` (the rhythm gym: tuplets and polyrhythms). Keep recordings, years and books accurate. Content only some pages show is loaded on demand by `lazy.js` (`loadEssays` for the style essays in `essays-*.js`, `loadScience`, `loadGuides`, `loadDrills`, `loadLessons`; draw with `whenLoaded` for a page or `drawWhenLoaded` inside a tool) so it stays out of the first download; dynamic `import()` chunks are still precached, so they work offline. `D.TECHNIQUES`, `D.DRILLS` and `D.LESSONS` start as a build-time index of their short fields (`virtual:content-index`, made by `scripts/content-index.mjs` from the content files; the fields are listed in `INDEX_FIELDS`) and the full objects are merged in when loaded: code that reads a long field (a guide's `mechanics`, a drill's `variations`, a lesson's `body`) must load first.
- `src/countgrid.js` (plain functions, `test/countgrid.test.js`): count grids for the drill pages. `phraseGrid` lays a written phrase on count slots ("1 e & a", or a drill's own `count`, e.g. a flamenco compás), with the backing's own part (`backingRows`: the clave, the target track) beside it and a "play on" line per bar naming each note and its count; `patternGrid` does the same for hand-written patterns (a variation's `grid: { rows: { thumb: '...x..x.' } }`, `x` hit, `X` loud, `-` held). A drill's `grid` sets the count for all its variations. The rhythm library's grid (`RhythmGrid` in `src/tools/rhythm.js`) takes `count` (labels per step) and `alt` (a second, slow count row, as the clave rhythms show the two-bar count), and each rhythm gets its region's glossary (`words` in `src/content/rhythms-var.js`). Drill and rhythm text uses these counts: one bar of clave is 1 e & a 2 e & a 3 e & a 4 e & a.
- `src/theory.js`: chord-symbol parsing, note spelling, diatonic chords. `chordMidis` is close position, kept for ear training.
- `src/voicings.js`: guitar chord shapes on the current tuning and capo (`voicings` lists playable shapes best first; `guitarMidis` and `progressionMidis` give the notes to strum, the latter staying near the last chord). Used by the chord demos (explorer, circle of fifths, lessons, repertoire), not by the ear trainers. `test/voicings.test.js` checks every chord on every root and tuning.
- `src/curriculum.js`: the smart practice engine. Every content item (scale on the neck, technique, rhythm, tune, lesson) has a memory stability in days (FSRS-style recall curve); it plans a session for the minutes the player has now, taking earlier sessions that day into account, caps new material per day, follows the player's ranked styles, rotates warm-up key/pattern/position/tempo, and grades blocks from tool signals (`hooks.signal(itemId, data)`) or a one-tap rating. Parameters follow `src/content/science.js` (verified research, shown in the app).
- `src/notation.js` (SVG staff renderer, no fonts; chords as `chord: [midi…]` on one stem, triplets as `tup: 3` with a 3 or a bracket, rhythm slashes, accents, staccato and `repeat` signs), `src/content/reading.js` (44 sight-reading levels, one new idea each, in `STAGES`; the Band charts stage adds accents and staccato (`acc`, `stac` on a note), repeat signs (`piece.repeat = [first, last]` bar, played twice through `playOrder`, `eventStarts`, `attacks` and `playLength`; `pieceLength` stays the written length), tab under the staff (`lv.tab`, `tabFor` in the tool, on your tuning) and rhythm slashes with chord symbols (`slash: true` notes on the middle line, `piece.chords`; a slash's attack carries its chord in `sym`, strummed by Hear it and scored by onset only); a level's `position` (2nd, 5th, 7th, 9th, with `posNotes(p)` for its range) is shown on the melody card; each level carries the fields of the one before unless it sets them, see `PATH`; generators for melodies of 4 to 16 bars in four-bar phrases, rhythms, thirds and sixths, chord progressions and chord melody) and `src/tools/reading.js` (the Sight-reading tool: notes, rhythm, melody, with mic scoring; `playRun` plays a run of pieces back to back on a grid of twelfths of a quarter, the next one appearing at its count-in bar, and keeps the line being read on screen; a white-paper staff, `settings.readingPaper`; a Sharps and flats switch, `settings.readingAcc`, runs any level through `withAccidentals` in `src/content/reading.js`: every note in its range, so sharps and flats beside the notes in Notes, and more chromatic notes in melodies, with its keys and rhythm unchanged). The fourth mode, Your scores (`scoresMode`, opened from the Sight-read it button under each score in the Library list (`sightFile` in `src/ui/library.js`: the entry's own score before the notes read from a page), a file's "Sight-read it" or the score viewer's Sight-read button (`opts.sightread` of `openScore`, which saves fixes first) with `params: { mode: 'scores', entry, file }`), reads the top line of a Library MusicXML, `.mxl`, MIDI or `.wwscore.json` file on this device (`READABLE_MELODY` in `src/library.js`) as the whole score in one piece that scrolls as you read (the default; `sections(mel, 0)`: every repeat kept with its signs, `piece.repeats` when there are several, which `playOrder` and `renderStaff({ repeats })` take, and a repeat with a first ending written out) or a section of 2, 4 or 8 bars at a time: `src/scorepieces.js` (`readScoreMelody`, `sections`; `test/scorepieces.test.js`) cuts it into reading pieces (a low melody written an octave up, empty bars at the start left out, ties cut at the section's end, in the score's own time: any `n/d` that `okTime` in `src/notate.js` accepts, so 10/4, 13/8 and 16/4 stay as written, while Write by playing drafts keep to `TIMES`; repeat signs from the MusicXML, `fromMusicXML`'s `repeats: [{ s, e, first }]` in quarters: the key signature and the score's own flats or sharps (`fromMusicXML`'s `fifths` and `spell`, so a page in C with E♭ and B♭ reads in C with flats, not in a key guessed from the notes); a repeat of up to a section's length stays whole in one section as `piece.repeat` and is read twice, a longer one or one with a first ending is read through and then its sections come again as `again`, "2nd time", without the first ending), and `melodyMode(root, lv, ctx, own)` plays them with the same count-in, cursor and mic check; they go into neither the reading library nor the level's record, and a score sends `hooks.signal('piece:<entry id>')`. The choice is `settings.readingOwn`. Melodies and Your scores have a Full screen view (`setFull` in `melodyMode`): the piece on one long line (`renderStaff({ oneLine: true })`, scaled to the height) that slides along as you read (`followAlong`), under one row of controls; `fullScreen(on, el)` in `src/native.js` asks the browser for full screen and, on a touch screen, landscape, and in the Android app calls the app's own `Immersive` plugin (`ImmersivePlugin.java`, registered in `MainActivity`), which hides the system bars and turns the screen to landscape, since the WebView can't go full screen itself. Levels were renumbered in schema 8 (`src/sync.js` maps the old 16 onto the path) 9 (the positions up the neck went in around fifth position) and 10 (the band charts before Everything), all through `moveLevels`, so a new level goes at the end of its stage only with a migration; `test/content.test.js` checks that each figure first appears at its own level. `src/readlib.js` keeps every generated rhythm and melody you read (compactly encoded, in `state.readLib`; slashes, articulations, repeats and chord symbols included); missed ones come back for a re-read after a gap, one piece in three, and you can star, replay or delete them.
- `src/notate.js` (plain functions, `test/notate.test.js`) and `src/tools/notate.js` (+ `notate.css`): Write by playing (Train → Guitar, tool `notate`). The mic's `note` and `pitch` events (or taps on the fretboard) become a draft (`{ title, bpm, time, key, grid, hold, notes: [{ s, e, midi }] }`, beats in quarters, sounding pitch, kept as played) stored on the device only (`localStorage` key `ww-notate-draft`). `quantize` snaps to the grid and writes notation.js bars with ties split at beats and bar lines; `guessKey` (Krumhansl–Kessler), `placeFrets` (hand-position Viterbi on the current tuning and capo) gives the tab that `renderStaff({ tab })` draws under the staff; `toMusicXML` (treble 8vb plus a TAB staff, sounding pitches, as MuseScore exports guitar) and `toMidi` (type 0) open in MuseScore through `openBlob` (the Android app hands the file to MuseScore, else the share sheet; a browser downloads it). "Save to the Library" stores the MusicXML, the MIDI and the draft as `<title>.wwscore.json` in a Library entry (`addToLibrary`/`addFiles`; the entry id is kept with the draft so a second save replaces those files), and the Library opens it again with `openTool('notate', { params: { load: entryId } })`. Monophonic only.
- `src/routines.js`: routine block types (`BLOCKS`), templates, time fitting (`setTotal`, auto breaks), no-guitar swaps (`awayBlocks`).
- `src/audio.js`: Web Audio synthesis (Karplus-Strong guitar, percussion voices, look-ahead `Loop` scheduler, tanpura `Drone`). `note`, `strum` and `hit` take an optional output node. `strum` is humanised (`strumPlan`: 8–25 ms per string, `o.dir: 'up'` strokes, a few cents of detune, all strings damped together); `note` takes `o.detune` (cents) and `o.release` (seconds). Output chain: `note` plays on a guitar channel and `hit` on a percussion channel (`A.channel(name)`: level, slight stereo placement, a send to a shared 0.5 s room reverb), then master, the compressor (the only look-ahead node, so latency stays as it was) and a soft limiter (a WaveShaper fed at a quarter level so its curve covers ±4 × full scale, unchanged below −3 dBFS). The context's `latencyHint` comes from `settings.audioOutput` (per device, Settings → Display → Sound output; `latencyHintFor`): `auto` asks for `playback` on Android, whose default low-latency path crackles on some phones, and `interactive` elsewhere; it is read once, when the audio starts. `test/output.test.js`. The band and the sampled instruments keep their own buses into master. Play buttons start over: call `A.fresh()` first, which fades out the one-shot sounds still ringing (every source not scheduled by a running `Loop`), cancels the ones not yet started, timers set with `A.later(fn, ms, onCancel)` and loops started with `{ shot: true }` (their `onEnd` runs); the metronome, drones, the band and other loops are left alone. The Quiz component does this for `play`, `compare` and extra buttons. `Loop.stop()` cancels what it had scheduled ahead, and a loop that wakes after the page slept skips the steps that went by instead of playing them in one burst. `test/fresh.test.js`.
- `src/samples.js`: sampled instruments. Each instrument (`src/content/samples.js`, generated) loads on first use with fetch + decodeAudioData; `play(id, midi, when, vel, dur, out)` returns null until it has, and the caller plays its synth voice instead. Velocity layers, round-robins, nearest sampled pitch, attack found in the decoded audio. The files live in `public/samples/<id>/` (mono 44.1 kHz MP3), credited in `public/samples/LICENSES.md` (CC0 or CC-BY only) and built from the recipes in `scripts/samples/recipes.mjs` by `scripts/samples/build.mjs` (needs ffmpeg). The service worker caches them at runtime (cache `ww-samples`), not in the precache; Settings → Display → Sounds downloads them all. `test/samples.test.js` checks every file exists, is mono 44.1 kHz MP3 and has a licence entry.
- `src/guitars.js`: the recorded guitars behind `A.note()` (so every strum, fretboard tap, ear-training note and the band's guitar comping), registered with `A.setNoteSampler`. `settings.guitarSound` picks `nylon` (default), `steel` or `synth` (Settings → Display → Sounds); the recordings (FluidR3 GM, one velocity per semitone, CC BY 3.0 renders of an MIT SoundFont) are made darker as well as quieter for soft notes (`cutoffFor`). `A.note(…, { synth: true })` skips them. Loaded on the first tap; the synth plays until then. `test/guitars.test.js`.
- `src/drumkit.js`: the recorded percussion behind `A.hit()` (registered with `A.setHitSampler`). Maps each voice to a sample set, with low/mid/high chosen by the rhythm's region (`kitFor`: congas for Cuba and West Africa, darbuka for Arabic, Turkish/Balkan and Persian, cajón for flamenco, drum kit elsewhere). The tabla and the chick (a guitar chop) stay synthesized. `prepare()` loads a rhythm's sounds when it is shown; the metronome's woodblock loads on the first tap. `hit(type, when, vel, out, { kit, region, synth })`; mic calibration forces the synth click. `test/drumkit.test.js` checks every voice has a recording.
- `src/band.js`: the Repertoire gym's backing band (`Band`). Swing: walking upright bass, rootless piano voicings with voice leading and varied comping rhythms, synthesized ride kit; bossa nova; other grooves from the `GROOVES` patterns. Parts sit on a bus with room reverb and can be muted (e.g. bass alone). `barAt(time)` drives the "follow the form by ear" check. Tunes can carry a `form` (`[[label, bars]]`) in `data.js`.
- `src/engine.js`: your guitar (`TUNINGS`, `STRINGS` updated in place for tuning and capo, `setGuitar`; left-handed fretboard; letter or solfège note names applied to `D.NOTE_NAMES`), skill model, spaced repetition, mastery and level unlocks, placement test, the adaptive (smart) plan, custom routines, the running session, lessons done, recordings heard, practice journal, persistence, backup export/import.
- `src/ui/core.js`: UI helpers (`h`, `s`, `Fretboard`, `toast`, `Quiz`), tabs and routing (old `#ear`, `#rhythm`, `#play`, `#atlas` links are aliases), the tool registry (`tool`, `openTool`), placement runner. `PAGES` lives here and is filled in by the page modules; `hooks` lets `session.js` plug in without import cycles.
- `src/ui/session.js`: the practice session runner: wall-clock timer that keeps counting with the screen off, session bar on each tool, time-up chime (then it waits for Done · next; moving on by itself is opt-in, `settings.autoAdvance`, for every session), wake lock, finish screen and journal.
- `src/ui/smart.js`: the smart planner ("How much time do you have right now?"), learning preferences (ranked styles, pace, daily goal) and the science page.
- `src/ui/routine.js`: the Routine tab (routine editor with drag reorder, durations, templates, smart plan, session overview).
- `src/mytunes.js`: your own tunes for the Repertoire gym. Reads a typed chord chart (bars split by `|` or lines, `%` repeats a bar, common spellings such as `C-7`, `CΔ7`, `Cø` normalised to `theory.js` symbols) and form (`AABA` or `A8 B8`), checks a draft (`checkTune`) and makes a saved tune safe to play (`playable`, since it may come from another device). Saved in `state.tunes` (`E.listTunes`, `saveTune`, `deleteTune` with a `tune:` tombstone) in the same shape as `D.TUNES`, so the Repertoire gym and the band play them alike; they are not in the planner's catalogue, so they send no `hooks.signal`. A Transcribe song becomes a draft tune (Sections card → "Make a tune for the band"): `songLayout` turns the beat grid and sections (or the loop, or the whole song) into bars and a form, the Transcribe plugin guesses a chord per bar or half bar from the recording (`songChords`, using `splitBar` and `chordName`) and opens the Repertoire editor with `params.draft`; the saved tune keeps the song's id in `song` for the link back.
- `src/harmony.js` (plain functions, `test/harmony.test.js`) and `src/content/tunes-harmony.js` (loaded by `loadTuneNotes`, attached as `t.harmony`): how the changes of every Repertoire tune work and how to solo over them (`SOLO`, attached as `t.harmony.solo`: `harmony` targets and `theory` scales, drawn by `SoloTips` in `src/ui/solo.js`; the improvising drills have the same in `src/content/drills-solo.js`, attached as `d.solo` by `loadDrills`). Per tune an intro, `rn` (one Roman numeral per chord, bar by bar, relative to the major scale of the section's key, so ♭III in C is E♭; `V7/ii` points to ii; `ii7:G` puts one chord in another key) and `sections` (`bars: [from, to]` counted from 1, `key` such as `Bb` or `Gm`, an optional display `name` such as `D Hijaz`, title, text, notes to aim for, scale). The Repertoire gym shows the numerals under the chords (with the key wherever it changes, transposed with the tune) and a "How the changes work" card with a loop button per section. The test checks every numeral's root and 3rd against its chord, so keep it passing when a chart changes.
- `src/melody.js` (plain functions, `test/melody.test.js`) and `src/content/tunes-melody.js` (loaded by `loadTuneNotes`, attached as `t.melody`): the melody under a Repertoire tune's chart. A melody is notes `{ s, e, midi }` (quarters from bar 1, sounding pitch, the Write by playing draft shape). The app has its own, original melodies only for the tunes that are a progression rather than a song (the blues, rhythm changes, the vamps), written as text (`parseMel`: `pitch:quarters`, `r:` rest, `-:` hold, bars split by `|`); the standards still under copyright have none, so never add their melodies. Pan adds one from Write by playing (`openTool('notate', { params: { forTune: { id, name } } })`, whose "Use it as the melody" saves it), from a Library entry's score or `.wwscore.json`, or from a file (`readMelodyFile`: MusicXML, compressed `.mxl` via `unzipMxl`, or a draft; `fromMusicXML` takes the first part's top staff and voice and applies `<transpose>`). Those are kept in `state.melodies` (schema 7, by tune id, packed `[s, e, midi]`, `mel:` tombstones; `E.getMelody`, `saveMelody`, `deleteMelody`) and win over the app's own. The Repertoire gym draws it as a lead sheet (`melodyBars` writes it at concert pitch, or an octave up when it lies low as a guitar recording does, and spells notes outside the key as the chord does with `spellOver`; `renderStaff` takes `chords` per bar and `barBands`) that follows the band and transposes with it, and the band plays it on the guitar sound (`Band({ melody: { notes, shift, on } })`, `set({ melodyOn })`, eighths swung in swing and shuffle) unless muted with "Hear the melody".
- `src/library.js` (+ `src/libfiles.js`, `src/ui/library.js`, `library.css`): the Library tab. Score files (PDF, MusicXML, MuseScore, Guitar Pro, MIDI, audio), photos of scores (camera or gallery) and songs, each with a status (want to learn, learning, learned), composer, notes and link. The details are `state.library` (schema 6, merged by id with the files listed on either copy; `lib:` and `libfile:` tombstones); the files stay in this device's IndexedDB (`world-woodshed-library`) and never go into the progress file, backups or localStorage, because photos and PDFs run to tens of MB. When automatic GitHub sync is on, `src/libsync.js` syncs them as separate files in the same repository (`world-woodshed-library/<file id>-<name>`, Contents API, up to 50 MB each): after each progress sync it uploads what only this device has and deletes what has a `libfile:` tombstone, and opening an entry downloads its missing files (by itself up to 25 MB, otherwise one tap each). Without it, another device lists them as "on another device". `ghsync.js` exposes `repoCall`, `repoDir` and `onSynced` for this. Entries marked learning or learned are items of the smart plan (`piece:<entry id>` in `src/curriculum.js`, `pieces()`, `choosePiece`): a learning piece joins sessions of 15 minutes or more without using the day's budget of new material, a learned one comes back when due, and the `piece` tool (registered in `src/ui/library.js`, block type `piece`, time counted under the `pieces` skill key in Statistics) opens its score, PDF or pages; the entry page's Practice card rates practice done outside a session. Other tools add to it with `addToLibrary({ title, by, notes, status, source, files })` and `addFiles(entryId, files)` and read a file back with `getFile(fileId)`; the page offers `openTool('notate')` when that tool exists. Files are read inside the app, each viewer its own chunk loaded on first use: photos in the image viewer, PDFs in `src/ui/pdfviewer.js` (pdf.js, the legacy build because the modern one needs `Map.getOrInsertComputed`, which Android WebViews lack; pages drawn as they scroll into view; precached), and MusicXML, Guitar Pro and MIDI in `src/ui/scoreview.js` (alphaTab, MPL-2.0: notation, tab or both, playback with a cursor through its SONiVOX sound font, speed, size, part). A MIDI file is read by `src/midiread.js` (`parseMidi`, `midiToDraft`: the top line, drums left out; `test/midiread.test.js`) and shown through `toMusicXML`. The `@coderline/alphatab-vite` plugin copies alphaTab's `font/` and `soundfont/` into the build; those, its worker and worklet and the `scoreview` chunk are left out of the precache and cached on first use instead (`ww-score`, CacheFirst), so open a score once online before relying on it offline. Other formats (.mscz, audio) open through `openBlob` in `src/native.js`: in the Android app a VIEW intent (`@capacitor/file-viewer`, so MuseScore or the phone's player), falling back to the share sheet (`shareBlob`) for types the phone knows no app for; on the web they are shared or downloaded. Those buttons stay as a second choice beside Read. `test/library.test.js`, `test/libsync.test.js` (a faked Contents API; `test/fakeidb.js` is a shared fake IndexedDB).
- `src/omr/` (plain functions, `test/omr.test.js`) and `src/ui/recognize.js`: score recognition, all on the device (Pan chose no cloud service). One reader for PDFs and photos: `prepare.js` scales a page so a staff space is about 20 px, binarizes it (`image.js`: local mean, so shadows in photos come out clean), finds staves in vertical strips (bent and slanted photos; six-line groups are tab and skipped), levels it and removes the staff and ledger lines; `detect.js` finds filled heads (distance to paper), hollow heads (holes), stems, beams or flags at the stem's free end, dots and bar lines, and hands other pieces to `classify.js` (k nearest neighbours over `templates.js`, made by `scripts/omr/train.mjs` from pages engraved by `scripts/omr/make-pages.py` with Verovio in five SMuFL fonts); `assemble.js` turns them into clef, key, time, bars, voices (two when stems go both ways and the bar holds twice its length) and pitches, evens out bars that don't add up (triplets, a filler rest or a cut) and lists them; `musicxml.js` writes MusicXML with those bars in `<miscellaneous-field name="ww-check-bars">`, which the score viewer shows. It runs in `omr.worker.js`, a page at a time. The Library reads a PDF by itself when it is added (pdf.js draws each page 2400 px wide) and photos on "Make it playable", saving `<name> (notes read).musicxml` in the same entry. Measure changes with `node scripts/omr/bench.mjs DIR` on pages from `make-pages.py` (`--photo`, `--hand`); at the time of writing printed pages read 95% of melody pitches in order and photographed ones 96%, and the handwriting stand-in (a handwritten-style font, warped) 88%. Real handwriting does worse. Those generated pages have no tab, fingerings or tempo marks, which real guitar PDFs do: MuseScore guitar scores (staff over tab, fingering digits, p/i/m, dynamics) read 1% of melody pitches before the reader learned them and 94% after, on 14 scores (not in the repository, no licence). What it takes: `prepare.js` tries each common line spacing (`staffMetrics` returns `cands`; the tab's six wider lines can outnumber the staff's) and keeps the one that explains the most staves; time-signature digits must sit inside the staff (not a tempo mark's "= 104"), and a stacked digit that the classifier calls something else is matched against the digits only (`classify(f, k, only)`); a head beyond the staff needs its ledger lines (`ledgersFor`), so fingering digits and dynamics there are not notes; a dot must stand alone on the page (`aloneIn`), not be a bit of a digit cut by a staff line; a whole note under up-stemmed notes is the lower voice (`partition` in `assemble.js`, also used to guess the time from bar lengths); a staff row with no key read counts as C when the systems vote; `smoothKnots` drops knots a whole line off their neighbours. Pan's own Sibelius PDFs (lead sheets, a piano and bass score, a full score with its parts after it, in 10/4, 12/8, 13/8 and 16/4) added: a stem with no head looks for a hollow head's hole with the lines in (a half note's ring touching a staff line opens when the line is taken out), round and not boxed in by lines, not beside a flagged stem, not in a symbol; `guessTime` takes any whole number of beats or eighths; the key's signs must sit at their own staff positions (`KEY_POS`), and a lone sign right before a head at its height is that note's accidental; a clef only at the start of a line (a chord on one stem looks like one); `countHooks` counts only beams and flags hanging from the free end (a thick ledger line crossing a low note's stem is not one); and `buildScore` leaves out pages after the score whose systems all have fewer staves (the separate parts, `partsFrom`, reported in the Library). A second pass on those (every bar of Bhoopali and Marwa's score now matches the page, none evened out) added: the other heads of a half-note chord are looked for at every staff position along its stem with the lines in (`hollowAt`: paper in the middle, a ring all round within two thirds of a space and thick at both sides, so not the paper between a stem and a rest), and of two heads a step apart on one side of a stem the clearer ring is kept (the paper between two touching rings is not a head); one stem's heads are all filled or all hollow, and a hollow "head" on a stroke beside a flagged stem is the flag's loop; a filled blob split at its narrow waist (heads a third apart) or column (a second, `sideBySide`); a head between two staves goes with the staff whose ledger lines it has, and its accidental with it; a whole note on a ledger line is tried as a ring; one clef to a line; a rest above or below the staff with letters beside it is text; a tie touching a flag is not another flag (`countHooks`); rests and dots that touch a stem or head are found by taking the stems and heads out of that ink; a percussion clef (two thick strokes) marks a drum staff, which `buildScore` leaves out (`drums`, reported in the Library); a lone key sign must sit exactly where the key's first sign goes (an F♯ an octave down is the note's sharp); a stretch from the clef to a forward repeat is not a bar; and whole rests beside a note keep their four beats when the bar holds them (16/4). Test with pages drawn as the app draws them, not only with `pdftoppm`: pdf.js smooths edges, so staff lines come out about 2.6 px instead of 1.8 at 2400 px wide, and what passed on poppler pages failed there (an unread time signature in a font the classifier doesn't know taken for a half note, chord rings on lines missed, a flag's loop taken for a head, a letter touching the next taken for a rest); `hollowAt` looks above and below a line however thick, a stacked piece that fills the staff near the line's start and reads as nothing is an unread time signature (`timeUnread`, the time then guessed), and the word check lets letters touch. To get the app's pages, hook `Worker.prototype.postMessage` in Playwright and save each `{ type: 'page', gray }` as PGM. Still not read: grace notes, scores that hide empty staves on some systems (rows then line up by count only), and drum parts. Ties (a thin curve just above or below two notes in a row at one staff position, `findTies` in `detect.js`, written per pitch) and repeat signs (two dots in the middle spaces beside a bar line, `findRepeats`; `score.repeats` as `[first, last]` bars, written as MusicXML repeat bar lines that alphaTab plays) are read; `make-pages.py --marks` makes pages with both, and the bench reports them. A reading's notes can be fixed in the score viewer (Fix notes, only for `(notes read).musicxml` files): tap a beat (alphaTab's `beatMouseDown`), then move it a line or space, sharpen, flatten, change its length (rests fill what a shorter note gave up), make it a rest or a note, tie it to the same note after it or take a tie off (`toggleTie`), or delete it, with Undo; Key sets the key signature for the whole score (`setKey`: notes with a printed accidental, after one in the bar, or tied over keep their pitch, the rest take the new key's). ## Conventions

- No frameworks and no runtime requests to other sites; everything is bundled so it works offline. The one exception is opt-in: automatic sync through the player's own private GitHub repository (`src/ghsync.js`), which talks only to `api.github.com` (the progress file, and the Library's files beside it) with a fine-grained token kept in this device's `localStorage` (key `ww-gh-sync`), never in the state, sync files or backups. The Android app's Check for updates also asks `api.github.com` for the latest release, without a token and only when tapped.
- New tabs or tools can be added as a plugin: export a function that takes the `UI` object and add it to the list in `src/main.js` (pushing onto `window.WW_PLUGINS` still works too).
- Persistence: `engine.js` saves state to `localStorage` and a copy in IndexedDB, and asks for persistent storage. When `window.claude` exists (inside a claude.ai Artifact with the `db` and `user` capabilities), it also syncs to the private database (chunked under `data/users/<id>/`, live across devices). Keep that guard.
- Saved state has a `schema` number. Changing its shape means adding a migration in `src/sync.js` (`MIGRATIONS`), never dropping old data, and teaching `merge()` about any new top-level key. A failed save is tracked in `engine.js` (`saveHealth`, `onSaveHealth`: `ok`, `idb-only` when localStorage fails but IndexedDB has it, `failing`, plus `stale` after a day without a good save) and shown as one quiet banner by `src/ui/savebanner.js`; `test/persistence.test.js` loads a saved state from every past schema (`test/fixtures/save-schema-*.json`; add one when you add a schema). Every copy (IndexedDB, cloud, sync file) is merged, not overwritten: practice time is kept per device in `state.hdev` and `history` is rebuilt from it; deletions leave a tombstone (`E.tombstone`). A merge is folded into the existing state objects (`patchInPlace` in `engine.js`; arrays are replaced), so an open tool that holds part of `E.state` (an exercise's tempo record, a skill's items) stays live across a sync or an import. Device-only settings (latency, mic) are listed in `DEVICE_SETTINGS`.
- Transcribe stores loaded audio in IndexedDB on the device only; song setups save with the rest of the state.
- Text from the player or another device (journal notes, song titles and links, routine names, anything in an imported backup or sync file) is only ever set with `h()`/`textContent`, never parsed as HTML; `innerHTML` is only cleared or set to a bundled SVG icon (`test/safety.test.js` checks this). Links from saved data are opened only if they are `http(s)`.
- Microphone input is opt-in. `src/listen.js` analyses it on the device (pitch, note onsets with exact timing); nothing is recorded or sent. Tools subscribe with `Mic.on(type, fn)` and the mic closes when the last listener unsubscribes. Every mic feature must also work by tapping.
