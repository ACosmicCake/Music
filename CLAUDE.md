# Notes for agents

The app is in `world-woodshed/`, a Vite project with plain JavaScript ES modules and no framework. It is an installable PWA (vite-plugin-pwa) deployed to GitHub Pages by `.github/workflows/deploy.yml`.

Run `npm install` then `npm run dev` (or `npm run build && npm run preview` to test the service worker) inside `world-woodshed/`, and drive it with Playwright to check a change. `npm test` (Vitest, `test/`) covers state migration and device merging (`src/sync.js`), chord parsing and diatonic harmony (`theory.test.js`), the skill model and backups (`engine.test.js`), the memory model and session planner (`curriculum.test.js`), playing to notation and the MusicXML/MIDI files (`notate.test.js`), routine time fitting (`routines.test.js`), practice statistics (`stats.test.js`), the time-stretch (`stretch.test.js`), your own tunes (`mytunes.test.js`), the Library (`library.test.js`, `libsync.test.js`, `midiread.test.js`), the reading library (`readlib.test.js`), count grids (`countgrid.test.js`), the guitar montunos (`montunos.test.js`), score recognition and its MusicXML (`omr.test.js`), your music taste from Spotify and favourite players (`taste.test.js`) and Roman numerals for the jazz standards (`harmony.test.js`), game mode's high scores and the rules of its eight games (`games.test.js`), the tuner's arithmetic (`tuner.test.js`), chord naming and hearing (`chordid.test.js`), the scale finder (`scalefind.test.js`), arpeggios on the neck and through the changes (`arpeggios.test.js`), the Constraint roll's rules (`constraints.test.js`), and checks the content data (rhythm lengths, chord symbols, drill bars, reading generators). `npm run lint` runs ESLint (`eslint.config.js`: `eslint:recommended`, with unused names as warnings); both workflows run lint and tests before building. Tests that load `engine.js` import `test/env.js` first (an in-memory `localStorage` and a stub `document`) and pin the clock with `vi.setSystemTime`.

## Files

`src/main.js` imports everything in order and boots the app:

- `index.html`: page shell only.
- `src/styles.css`: all CSS (design tokens on `:root`, dark mode via `prefers-color-scheme` and `data-theme`). Fonts are bundled from `@fontsource` so the app works offline. A compact layout for small phones (3-inch screens such as the Unihertz Jelly Star) lives under `html.compact`, set by `applyDisplay()` in `src/ui/core.js`: automatic below 380 × 640 CSS px or chosen in Settings → Display, with a text size (`html[data-text]`); both are per device (`DEVICE_SETTINGS`). Check new UI at 240 px wide as well as on a normal phone.
- `src/data.js`: content. Intervals and anchor songs, chords, progressions, world scales and ragas/maqamat, rhythm cycles, tunes, grooves, technique exercises, styles (atlas regions). It merges in `src/content/`.
- `src/content/`: long-form content. `styles-a.js`, `styles-b.js` (deep-dive fields for the original regions: history, sub-styles, how it works, listening path, players, study, practice) `styles-new.js` (eight whole new styles) and `styles-more.js` (four more: Southern Africa & Madagascar, Mexico, Colombia & Venezuela, mainland Southeast Asia, with their essays in `essays-7.js` and `essays-8.js`, drills in `drills-c.js`, rhythms in `rhythms-new.js`, a groove and a World grooves tune each); `lessons.js` (the theory course); `rhythms-new.js` (more rhythms per style, appended to `RHYTHMS`) and `rhythms-var.js` (variations, fills, cycles, tempo range and tips for every rhythm, attached as `r.var`; the player's own part never changes in a variation); `drills-a.js`, `drills-b.js`, `drills-c.js` (four or five style drills per style, `D.DRILLS`; `drills-c.js` writes a double stop or chord on one stem as `67+71:8`, stored as `n.ch` like the montunos); `drills-montunos.js` (six more Cuba drills: guitar montunos in 3-2 and 2-3 son, minor, salsa octaves, guajira and cha-cha-chá; written on a sixteenth grid with `S(rhythm, notes)`, where `64+60` is a double stop or chord on one stem, `n.ch`, drawn on one stem and played together by the drill page; `test/montunos.test.js`); `exercise-vars.js` (variations, speed burst and listening cue per technique exercise, `ex.vars`); `gym.js` (the rhythm gym: tuplets and polyrhythms). Keep recordings, years and books accurate. Content only some pages show is loaded on demand by `lazy.js` (`loadEssays` for the style essays in `essays-*.js`, `loadScience`, `loadGuides`, `loadDrills`, `loadLessons`; draw with `whenLoaded` for a page or `drawWhenLoaded` inside a tool) so it stays out of the first download; dynamic `import()` chunks are still precached, so they work offline. `D.TECHNIQUES`, `D.DRILLS` and `D.LESSONS` start as a build-time index of their short fields (`virtual:content-index`, made by `scripts/content-index.mjs` from the content files; the fields are listed in `INDEX_FIELDS`) and the full objects are merged in when loaded: code that reads a long field (a guide's `mechanics`, a drill's `variations`, a lesson's `body`) must load first.
- `src/countgrid.js` (plain functions, `test/countgrid.test.js`): count grids for the drill pages. `phraseGrid` lays a written phrase on count slots ("1 e & a", or a drill's own `count`, e.g. a flamenco compás), with the backing's own part (`backingRows`: the clave, the target track) beside it and a "play on" line per bar naming each note and its count; `patternGrid` does the same for hand-written patterns (a variation's `grid: { rows: { thumb: '...x..x.' } }`, `x` hit, `X` loud, `-` held). A drill's `grid` sets the count for all its variations. The rhythm library's grid (`RhythmGrid` in `src/tools/rhythm.js`) takes `count` (labels per step) and `alt` (a second, slow count row, as the clave rhythms show the two-bar count), and each rhythm gets its region's glossary (`words` in `src/content/rhythms-var.js`). Drill and rhythm text uses these counts: one bar of clave is 1 e & a 2 e & a 3 e & a 4 e & a.
- `src/theory.js`: chord-symbol parsing, note spelling, diatonic chords. `chordMidis` is close position, kept for ear training.
- `src/voicings.js`: guitar chord shapes on the current tuning and capo (`voicings` lists playable shapes best first; `guitarMidis` and `progressionMidis` give the notes to strum, the latter staying near the last chord). Used by the chord demos (explorer, circle of fifths, lessons, repertoire), not by the ear trainers. `test/voicings.test.js` checks every chord on every root and tuning.
- `src/curriculum.js`: the smart practice engine. Every content item (scale on the neck, technique, rhythm, tune, lesson) has a memory stability in days (FSRS-style recall curve); it plans a session for the minutes the player has now, taking earlier sessions that day into account, caps new material per day, follows the player's ranked styles, rotates warm-up key/pattern/position/tempo, and grades blocks from tool signals (`hooks.signal(itemId, data)`) or a one-tap rating. Starred favourites (`src/favlist.js`, `favourites`, `chooseFav`) are mixed in for variety: one in a session of 10 minutes or more, two from 45, ranked after due reviews and new material, rotating to the one played longest ago (`favs` on each logged session); a favourite technique or drill is a catalogue item that keeps its schedule and, when first practised, doesn't use the day's new budget; a Rhythm gym exercise opens as `gym` with `ex`, a tool as its block type, and a game in the block type of its skill with `b.tool` and `b.title` (the session runner opens `b.tool`); swapping a block offers one too. Parameters follow `src/content/science.js` (verified research, shown in the app).
- `src/notation.js` (SVG staff renderer, no fonts; chords as `chord: [midi…]` on one stem, triplets as `tup: 3` with a 3 or a bracket, rhythm slashes, accents, staccato and `repeat` signs), `src/content/reading.js` (44 sight-reading levels, one new idea each, in `STAGES`; - `src/content/notenames.js` (plain functions, `test/notenames.test.js`) and `src/tools/notenames.js` (+ `notenames.css`): Note names (Train → Guitar → Reading and writing, and No guitar; skill `notenames`, routine block `notenames`). Name notes or chords on the treble staff, the bass staff or both as a grand staff, at real pitch (as piano and bass music is written, unlike Sight-reading's guitar octave). Three levels per staff and kind: inside the staff, then three ledger lines, then sharps and flats (both spellings are separate items); for chords, major and minor in root position, then inversions and diminished, then augmented, the four sevenths and any root. A chord item (`c:<staff>:<quality>:<inversion>`) gets a new root each time (`chordRoots`: only spellings with sharps or flats but not both, no E♯, B♯, C♭, F♭); on the grand staff the bass note goes in the bass clef and the chord in the treble. Chords are named (root, then quality) or note by note from the bottom up (`settings.staffNames.answer`). Notes can be answered by playing them (mic, any octave). The level open is per staff and kind (`openLevel`, the engine's 80% tried / 75% right rule); choices in `settings.staffNames`.
- `src/notate.js` (plain functions, `test/notate.test.js`) and `src/tools/notate.js` (+ `notate.css`): Write by playing (Train → Guitar, tool `notate`). The mic's `note` and `pitch` events (or taps on the fretboard) become a draft (`{ title, bpm, time, key, grid, hold, notes: [{ s, e, midi }] }`, beats in quarters, sounding pitch, kept as played) stored on the device only (`localStorage` key `ww-notate-draft`). `quantize` snaps to the grid and writes notation.js bars with ties split at beats and bar lines; `guessKey` (Krumhansl–Kessler), `placeFrets` (hand-position Viterbi on the current tuning and capo) gives the tab that `renderStaff({ tab })` draws under the staff; `toMusicXML` (treble 8vb plus a TAB staff, sounding pitches, as MuseScore exports guitar) and `toMidi` (type 0) open in MuseScore through `openBlob` (the Android app hands the file to MuseScore, else the share sheet; a browser downloads it). "Save to the Library" stores the MusicXML, the MIDI and the draft as `<title>.wwscore.json` in a Library entry (`addToLibrary`/`addFiles`; the entry id is kept with the draft so a second save replaces those files), and the Library opens it again with `openTool('notate', { params: { load: entryId } })`. Monophonic only.
- `src/routines.js`: routine block types (`BLOCKS`), templates, time fitting (`setTotal`, auto breaks), no-guitar swaps (`awayBlocks`).
- `src/audio.js`: Web Audio synthesis (Karplus-Strong guitar, percussion voices, look-ahead `Loop` scheduler, tanpura `Drone`). `note`, `strum` and `hit` take an optional output node. `strum` is humanised (`strumPlan`: 8–25 ms per string, `o.dir: 'up'` strokes, a few cents of detune, all strings damped together); `note` takes `o.detune` (cents) and `o.release` (seconds). Output chain: `note` plays on a guitar channel and `hit` on a percussion channel (`A.channel(name)`: level, slight stereo placement, a send to a shared 0.5 s room reverb), then master, the compressor (the only look-ahead node, so latency stays as it was) and a soft limiter (a WaveShaper fed at a quarter level so its curve covers ±4 × full scale, unchanged below −3 dBFS). The context's `latencyHint` comes from `settings.audioOutput` (per device, Settings → Display → Sound output; `latencyHintFor`): `auto` asks for `playback` on Android, whose default low-latency path crackles on some phones, and `interactive` elsewhere; it is read once, when the audio starts. `test/output.test.js`. The band and the sampled instruments keep their own buses into master. Play buttons start over: call `A.fresh()` first, which fades out the one-shot sounds still ringing (every source not scheduled by a running `Loop`), cancels the ones not yet started, timers set with `A.later(fn, ms, onCancel)` and loops started with `{ shot: true }` (their `onEnd` runs); the metronome, drones, the band and other loops are left alone. The Quiz component does this for `play`, `compare` and extra buttons. `Loop.stop()` cancels what it had scheduled ahead, and a loop that wakes after the page slept skips the steps that went by instead of playing them in one burst. A loop's `onVisual` runs when its step comes out of the speakers, checked every frame against `A.heard()` (the audio time being heard now, from `getOutputTimestamp`, which counts the real output delay on Android and Bluetooth and runs smoothly where `currentTime` jumps a whole buffer; `currentTime − latency()` without it), so a cursor keeps with the sound however far ahead it was scheduled; `opts.ahead` (default 0.12 s) schedules further ahead, and Sight-reading's `playRun` uses 0.3 s so a slow phone or a long score can't make the beat stumble. `eventToAudioTime` uses `heard()` too. `test/fresh.test.js`.
- `src/samples.js`: sampled instruments. Each instrument (`src/content/samples.js`, generated) loads on first use with fetch + decodeAudioData; `play(id, midi, when, vel, dur, out)` returns null until it has, and the caller plays its synth voice instead. Velocity layers, round-robins, nearest sampled pitch, attack found in the decoded audio. The files live in `public/samples/<id>/` (mono 44.1 kHz MP3), credited in `public/samples/LICENSES.md` (CC0 or CC-BY only) and built from the recipes in `scripts/samples/recipes.mjs` by `scripts/samples/build.mjs` (needs ffmpeg). The service worker caches them at runtime (cache `ww-samples`), not in the precache; Settings → Display → Sounds downloads them all. `test/samples.test.js` checks every file exists, is mono 44.1 kHz MP3 and has a licence entry.
- `src/guitars.js`: the recorded guitars behind `A.note()` (so every strum, fretboard tap, ear-training note and the band's guitar comping), registered with `A.setNoteSampler`. `settings.guitarSound` picks `nylon` (default), `steel` or `synth` (Settings → Display → Sounds); the recordings (FluidR3 GM, one velocity per semitone, CC BY 3.0 renders of an MIT SoundFont) are made darker as well as quieter for soft notes (`cutoffFor`). `A.note(…, { synth: true })` skips them. Loaded on the first tap; the synth plays until then. `test/guitars.test.js`.
- `src/drumkit.js`: the recorded percussion behind `A.hit()` (registered with `A.setHitSampler`). Maps each voice to a sample set, with low/mid/high chosen by the rhythm's region (`kitFor`: congas for Cuba and West Africa, darbuka for Arabic, Turkish/Balkan and Persian, cajón for flamenco, drum kit elsewhere). The tabla and the chick (a guitar chop) stay synthesized. `prepare()` loads a rhythm's sounds when it is shown; the metronome's woodblock loads on the first tap. `hit(type, when, vel, out, { kit, region, synth })`; mic calibration forces the synth click. `test/drumkit.test.js` checks every voice has a recording.
- `src/band.js`: the Repertoire gym's backing band (`Band`). Swing: walking upright bass, rootless piano voicings with voice leading and varied comping rhythms, synthesized ride kit; bossa nova; other grooves from the `GROOVES` patterns. Parts sit on a bus with room reverb and can be muted (e.g. bass alone). `barAt(time)` drives the "follow the form by ear" check. Tunes can carry a `form` (`[[label, bars]]`) in `data.js`. The Cuban grooves are `son` (3-2 clave), `son23` (the same started from its second half) and `chacha` (cowbell on the beat, güiro on the shaker, piano on the beat and the & of 4).
- `src/engine.js`: your guitar (`TUNINGS`, `STRINGS` updated in place for tuning and capo, `setGuitar`; left-handed fretboard; letter or solfège note names applied to `D.NOTE_NAMES`), skill model, spaced repetition, mastery and level unlocks, placement test, the adaptive (smart) plan, custom routines, the running session, lessons done, recordings heard, practice journal, persistence, backup export/import.
- `src/ui/core.js`: UI helpers (`h`, `s`, `Fretboard`, `toast`, `Quiz`), tabs and routing (old `#ear`, `#rhythm`, `#play`, `#atlas` links are aliases), the tool registry (`tool`, `openTool`), placement runner. `PAGES` lives here and is filled in by the page modules; `hooks` lets `session.js` plug in without import cycles.
- `src/ui/session.js`: the practice session runner: wall-clock timer that keeps counting with the screen off, session bar on each tool, time-up chime (then it waits for Done · next; moving on by itself is opt-in, `settings.autoAdvance`, for every session), wake lock, finish screen and journal.
- `src/ui/smart.js`: the smart planner ("How much time do you have right now?"), learning preferences (ranked styles, pace, daily goal) and the science page.
- `src/ui/routine.js`: the Routine tab (routine editor with drag reorder, durations, templates, smart plan, session overview). The learning plan and the templates are folded (`fold`), so the page is the planner or your routine first.
- `src/mytunes.js`: your own tunes for the Repertoire gym. Reads a typed chord chart (bars split by `|` or lines, `%` repeats a bar, common spellings such as `C-7`, `CΔ7`, `Cø` normalised to `theory.js` symbols) and form (`AABA` or `A8 B8`), checks a draft (`checkTune`) and makes a saved tune safe to play (`playable`, since it may come from another device). Saved in `state.tunes` (`E.listTunes`, `saveTune`, `deleteTune` with a `tune:` tombstone) in the same shape as `D.TUNES`, so the Repertoire gym and the band play them alike; they are not in the planner's catalogue, so they send no `hooks.signal`. A Transcribe song becomes a draft tune (Sections card → "Make a tune for the band"): `songLayout` turns the beat grid and sections (or the loop, or the whole song) into bars and a form, the Transcribe plugin guesses a chord per bar or half bar from the recording (`songChords`, using `splitBar` and `chordName`) and opens the Repertoire editor with `params.draft`; the saved tune keeps the song's id in `song` for the link back.
- `src/harmony.js` (plain functions, `test/harmony.test.js`) and `src/content/tunes-harmony.js` (loaded by `loadTuneNotes`, attached as `t.harmony`): how the changes of every Repertoire tune work and how to solo over them (`SOLO`, attached as `t.harmony.solo`: `harmony` targets and `theory` scales, drawn by `SoloTips` in `src/ui/solo.js`; the improvising drills have the same in `src/content/drills-solo.js`, attached as `d.solo` by `loadDrills`). Per tune an intro, `rn` (one Roman numeral per chord, bar by bar, relative to the major scale of the section's key, so ♭III in C is E♭; `V7/ii` points to ii; `ii7:G` puts one chord in another key) and `sections` (`bars: [from, to]` counted from 1, `key` such as `Bb` or `Gm`, an optional display `name` such as `D Hijaz`, title, text, notes to aim for, scale). The test checks every numeral's root and 3rd against its chord, so keep it passing when a chart changes.
- `src/melody.js` (plain functions, `test/melody.test.js`) and `src/content/tunes-melody.js` (loaded by `loadTuneNotes`, attached as `t.melody`): the melody under a Repertoire tune's chart. - `src/omr/` (plain functions, `test/omr.test.js`) and `src/ui/recognize.js`: score recognition, all on the device (Pan chose no cloud service). One reader for PDFs and photos: `prepare.js` scales a page so a staff space is about 20 px, binarizes it (`image.js`: local mean, so shadows in photos come out clean), finds staves in vertical strips (bent and slanted photos; six-line groups are tab and skipped), levels it and removes the staff and ledger lines; `detect.js` finds filled heads (distance to paper), hollow heads (holes), stems, beams or flags at the stem's free end, dots and bar lines, and hands other pieces to `classify.js` (k nearest neighbours over `templates.js`, made by `scripts/omr/train.mjs` from pages engraved by `scripts/omr/make-pages.py` with Verovio in five SMuFL fonts); `assemble.js` turns them into clef, key, time, bars, voices (two when stems go both ways and the bar holds twice its length) and pitches, evens out bars that don't add up (triplets, a filler rest or a cut) and lists them; `musicxml.js` writes MusicXML with those bars in `<miscellaneous-field name="ww-check-bars">`, which the score viewer shows. It runs in `omr.worker.js`, a page at a time. The Library reads a PDF by itself when it is added (pdf.js draws each page 2400 px wide) and photos on "Make it playable", saving `<name> (notes read).musicxml` in the same entry. Measure changes with `node scripts/omr/bench.mjs DIR` on pages from `make-pages.py` (`--photo`, `--hand`); at the time of writing printed pages read 95% of melody pitches in order and photographed ones 96%, and the handwriting stand-in (a handwritten-style font, warped) 88%. Real handwriting does worse. Those generated pages have no tab, fingerings or tempo marks, which real guitar PDFs do: MuseScore guitar scores (staff over tab, fingering digits, p/i/m, dynamics) read 1% of melody pitches before the reader learned them and 94% after, on 14 scores (not in the repository, no licence). What it takes: `prepare.js` tries each common line spacing (`staffMetrics` returns `cands`; the tab's six wider lines can outnumber the staff's) and keeps the one that explains the most staves; time-signature digits must sit inside the staff (not a tempo mark's "= 104"), and a stacked digit that the classifier calls something else is matched against the digits only (`classify(f, k, only)`); a head beyond the staff needs its ledger lines (`ledgersFor`), so fingering digits and dynamics there are not notes; a dot must stand alone on the page (`aloneIn`), not be a bit of a digit cut by a staff line; a whole note under up-stemmed notes is the lower voice (`partition` in `assemble.js`, also used to guess the time from bar lengths); a staff row with no key read counts as C when the systems vote; `smoothKnots` drops knots a whole line off their neighbours. Pan's own Sibelius PDFs (lead sheets, a piano and bass score, a full score with its parts after it, in 10/4, 12/8, 13/8 and 16/4) added: a stem with no head looks for a hollow head's hole with the lines in (a half note's ring touching a staff line opens when the line is taken out), round and not boxed in by lines, not beside a flagged stem, not in a symbol; `guessTime` takes any whole number of beats or eighths; the key's signs must sit at their own staff positions (`KEY_POS`), and a lone sign right before a head at its height is that note's accidental; a clef only at the start of a line (a chord on one stem looks like one); `countHooks` counts only beams and flags hanging from the free end (a thick ledger line crossing a low note's stem is not one); and `buildScore` leaves out pages after the score whose systems all have fewer staves (the separate parts, `partsFrom`, reported in the Library). A second pass on those (every bar of Bhoopali and Marwa's score now matches the page, none evened out) added: the other heads of a half-note chord are looked for at every staff position along its stem with the lines in (`hollowAt`: paper in the middle, a ring all round within two thirds of a space and thick at both sides, so not the paper between a stem and a rest), and of two heads a step apart on one side of a stem the clearer ring is kept (the paper between two touching rings is not a head); one stem's heads are all filled or all hollow, and a hollow "head" on a stroke beside a flagged stem is the flag's loop; a filled blob split at its narrow waist (heads a third apart) or column (a second, `sideBySide`); a head between two staves goes with the staff whose ledger lines it has, and its accidental with it; a whole note on a ledger line is tried as a ring; one clef to a line; a rest above or below the staff with letters beside it is text; a tie touching a flag is not another flag (`countHooks`); rests and dots that touch a stem or head are found by taking the stems and heads out of that ink; a percussion clef (two thick strokes) marks a drum staff, which `buildScore` leaves out (`drums`, reported in the Library); a lone key sign must sit exactly where the key's first sign goes (an F♯ an octave down is the note's sharp); a stretch from the clef to a forward repeat is not a bar; and whole rests beside a note keep their four beats when the bar holds them (16/4). Test with pages drawn as the app draws them, not only with `pdftoppm`: pdf.js smooths edges, so staff lines come out about 2.6 px instead of 1.8 at 2400 px wide, and what passed on poppler pages failed there (an unread time signature in a font the classifier doesn't know taken for a half note, chord rings on lines missed, a flag's loop taken for a head, a letter touching the next taken for a rest); `hollowAt` looks above and below a line however thick, a stacked piece that fills the staff near the line's start and reads as nothing is an unread time signature (`timeUnread`, the time then guessed), and the word check lets letters touch. To get the app's pages, hook `Worker.prototype.postMessage` in Playwright and save each `{ type: 'page', gray }` as PGM. Still not read: grace notes, scores that hide empty staves on some systems (rows then line up by count only), and drum parts. Ties (a thin curve just above or below two notes in a row at one staff position, `findTies` in `detect.js`, written per pitch) and repeat signs (two dots in the middle spaces beside a bar line, `findRepeats`; `score.repeats` as `[first, last]` bars, written as MusicXML repeat bar lines that alphaTab plays) are read; `make-pages.py --marks` makes pages with both, and the bench reports them. First and second endings are read too: `findEndings` in `detect.js` finds the bracket (a level, unbroken line above the staff with a hook down at its left), `cutBars` puts it on the bars it covers and `buildScore` numbers it from the repeat signs (the one closing with a backward repeat is the 1st, the next the 2nd), as `score.endings: [[first, last, n]]`, written as `<ending>` on the bar lines; `make-pages.py --marks` adds them and the bench reports them. Time signatures are read on every bar, not only at a line's start: `readStaff` keeps each stacked pair inside the staff (`s.times`, `timeOf`), `cutBars` gives a bar the one printed before its first note, and `buildScore` returns `times` (each bar's, null when the time never changes) for `fitBar` and `scoreToMusicXML` (a `<time>` where it changes); a stretch after a line's last bar line with no notes in it (a courtesy time signature) is not a bar. Time signatures and tuplet numbers in a text font (Finale's Maestro, Sibelius's), which the SMuFL examples don't cover, are read with `src/omr/digits.js` (`classifyDigit(f, 'time' | 'tuplet')`, made by `scripts/omr/train-digits.mjs` from pages `scripts/omr/digit-pages.py` draws in Liberation, DejaVu, FreeFont and Caladea; an "8" needs two loops, `holesIn`, as a 6 closed at the top by a staff line looks like one); two digits that don't touch are paired top half over bottom half. A tuplet's 3 above or below the staff with its bracket (the arms traced on the page with the lines in, `traceArm`, as taking the lines out removes arms near the staff), or over a beamed group, makes the notes and rests under it a triplet (`findTuplets` in `detect.js`, `e.tup` in `readStaff`). A sharp or natural that a flag runs into is part of the note's ink and so never classified: its two upright strokes beside the head are found among the strokes with no head. `test/omr.test.js` reads a page drawn by `scripts/omr/meter-page.py` (4/4, 5/4, 7/4, a courtesy 4/4, a bracketed triplet, a sharp touched by a flag). Pan's Finale lead sheet XG (4/4, 5/4 and 7/4 every line, triplet brackets, courtesy accidentals in brackets) reads all 90 bars and 418 notes, as pdf.js draws it and as poppler does. Not read: slurs, D.S. and coda, text (chord symbols), tab digits, grace notes. A reading's notes can be fixed in the score viewer (Fix notes, only for `(notes read).musicxml` files): tap a beat (alphaTab's `beatMouseDown`), then move it a line or space, sharpen, flatten, change its length (rests fill what a shorter note gave up), make it a rest or a note, tie it to the same note after it or take a tie off (`toggleTie`), or delete it, with Undo; Key sets the key signature for the whole score (`setKey`: notes with a printed accidental, after one in the bar, or tied over keep their pitch, the rest take the new key's). Fix notes is reached from the score viewer, from a Fix notes button beside Sight-read it in the Library list, and from Fix the notes in Sight-reading's Your scores card (`fixNotes(entryId, fileId, onSaved)` in `src/ui/library.js` opens the viewer with `opts.fix`; Sight-reading reloads the new file when a fix is saved). `src/scoreedit.js` (plain functions over the recognizer's MusicXML text, `test/scoreedit.test.js`) does the edits and rewrites the bars to check; the fixed file replaces the old one through `replaceFile` in `src/library.js` (a new file id, the old one tombstoned, its section tempos moved) when you leave Fix notes or close the score.

- Game mode (Train → Games, `games` in `TRAIN`; a 🎮 Play as a game button on a Rhythm gym exercise and in Intervals, Scale degrees, Fretboard notes, the Repertoire gym (preset tunes with more than one section letter) and Sight-reading (not Your scores), hidden inside a session block): `src/games.js` (plain functions, `test/games.test.js`) keeps personal high-score tables in `state.games` (schema 11: `{ <game>: [{ s, t, d, ...details }] }`, best first, `BOARD` = 10 each, merged in `merge()` by joining both copies on time and device; `E.gameScores`, `E.addGameScore`, `E.gameRank`) and the rules of each game; `src/ui/games.js` draws the table (`Leaderboard`) and the end card, and a game tool's tile shows your best (`game: '<id>'` on the tool). Scores never leave the player's own devices and sync. Every game is a tool on a real skill, so its time and answers count as practice. **The Tower** (`src/tools/tower.js`, skill `intervals`): a princess sings an interval from her window (a synthesized "ah" through three formants, or the guitar, `settings.towerSound`); right climbs a step, wrong slips one (`climb`), twelve steps a tower, each tower harder (`towerStage`: rising, falling, both, together, less time each tower), five wrong and the run ends; every answer goes through `E.record('intervals', …)` like the quiz. Three on the Rhythm gym's skills, each with its rules in `src/games.js` (taps matched to notes by `matchTaps`; nothing calibrates taps, so a screen's or speaker's steady delay is learned with `delayTracker` (the median of recent errors) and taken off before judging, `matchShifted`: Tightrope learns it in its first 8 bars, with the click on every beat, Two Drums, Parrot and Opening Night as they go): **Tightrope** (`src/tools/tightrope.js`, skill `tuplets`): play every beat while the click thins every `ROPE_BARS` (8) bars (`ropeStage`, `ropeClick`: every beat, 2 and 4, 1, 1 of every other bar, of every fourth); each note leans the walker by its signed error in beats (`leanAfter`: rushing forward, to the right, and the meter under it too; dragging back, a missed beat jolts, the first bar forgiven), `ropeFell` at a lean of 1; reaching the click on 1 of every other bar records the gym's `disp-bar`. **Two Drums** (`src/tools/twodrums.js`): the gym's polyrhythms in tier order, the beat side on the left drum and the other on the right (F/J or ←/→; taps only, as the mic can't tell the hands apart), rounds of a count-in and 4 bars (2 guided, 2 alone), `drumPassed` at 75% on each drum, three hearts, a lap 8 bpm faster after the last; each round records its exercise. **Parrot** (`src/tools/parrot.js`): a whistled phrase of sixteenth cells (`parrotCell`, syncopated from five beats) echoed straight back on the click, one beat longer each round (`echoPassed`: every note, at most one extra), three feathers, the dots hidden while you answer from four beats on; records `echo2` or `echo4`. A Rhythm gym exercise's Play as a game opens the game for its kind (`GAME_FOR` in `src/tools/rhythmgym.js`: polyrhythms on Two Drums, echo on Parrot, displaced clicks on Tightrope; the others have none). Updraft, a kite flown through the clouds, was taken out at Pan's request; its old scores stay in `state.games`. Every game's first screen explains it with `HowTo` (`src/ui/games.js`: the goal, then How to play, Scoring and when the run ends, open until you have a score in that game, then folded); keep it in step with the rules when they change. **Lighthouse Keeper** (`src/tools/lighthouse.js`, skill `degrees`): a cadence sets each harbour's key, then `SHIPS` (8) ships sound one note each on their horn; name its degree before the ship reaches the rocks (`harbourSecs`, less time each harbour; `harbourTier` opens one degree tier beyond yours from the third harbour; `shipPoints`), a wrong or late answer wrecks it and plays tonic then note, `WRECKS` (3) end the run; answers go through `E.record('degrees', …)`. **Firefly Hunt** (`src/tools/firefly.js`, skill `fretboard`): each round names a note (`fireflyRound`: naturals, then sharps and flats from round 5, two notes from round 10, less time each round); tap every place it sits, frets 0 to 12 (`positionsOfPc`), a wrong tap costs `FIREFLY_PENALTY` (2) seconds, a round that runs out costs one of three lives; every tap records `stringId:pc`; with the mic on, a played note catches its lowest firefly still out. **Lost in the Form** (`src/tools/formgame.js`, skill `repertoire`): the band plays a tune with a form of two letters or more, chart hidden; tap the letter of each section on its first beat (`formStarts`, `formLetters`, `formJudge`: within half a beat perfect, 1.25 good; the first A, straight after the count-in, is given); the first chorus lights the sections up, then each chorus is faster (+6 bpm) with less of the band (`PARTS`: bass and drums, then bass alone); a miss, wrong letter or a tap where no section starts costs one of three hearts; each chorus records the tune. **Opening Night** (`src/tools/opening.js`, skill `reading`): sight-reading where you never stop. An endless run of four-bar lines from `genMelody`, starting at your opened reading level (levels with chord slashes or repeats left out) at that level's slowest tempo, kept steady all run (the lines ahead are timed in it), the next line shown dimmed below; one level up every `SHOW_LEVEL_BARS` (8) bars. Wrong notes are cheap and stopping is dear: the crowd meter (`crowdAfter`) rises for notes played in time and falls a little for ones missed, but a silent bar (`barSilent`) costs `CROWD_SILENT` and the curtain falls (`curtain`) at an empty meter or two silent bars running; points per note in time (`showNotePoints`, more with the mic when the pitch is right), doubled for the bar after a slip if you kept going. Tap or mic; each line records the level's `:rhythm` or `:melody` item. The art (tower, princess, traveller, tightrope walker, parrot, lighthouse and ships, fireflies, the stage) is drawn in code and original; keep any new game's look and names original too.

## Conventions

- No frameworks and no runtime requests to other sites; everything is bundled so it works offline. The one exception is opt-in: automatic sync through the player's own private GitHub repository (`src/ghsync.js`), which talks only to `api.github.com` (the progress file, and the Library's files beside it) with a fine-grained token kept in this device's `localStorage` (key `ww-gh-sync`), never in the state, sync files or backups. The Android app's Check for updates also asks `api.github.com` for the latest release, without a token and only when tapped. Spotify (`src/spotifyauth.js`) talks to `accounts.spotify.com` and `api.spotify.com` only after the player connects it. Linking a device by code (`src/linkcode.js`) talks to `ntfy.sh`, only while a code is shown or typed, and sends it only the encrypted setup.
- New tabs or tools can be added as a plugin: export a function that takes the `UI` object and add it to the list in `src/main.js` (pushing onto `window.WW_PLUGINS` still works too).
- Persistence: `engine.js` saves state to `localStorage` and a copy in IndexedDB, and asks for persistent storage. When `window.claude` exists (inside a claude.ai Artifact with the `db` and `user` capabilities), it also syncs to the private database (chunked under `data/users/<id>/`, live across devices). Keep that guard.
- Saved state has a `schema` number. Changing its shape means adding a migration in `src/sync.js` (`MIGRATIONS`), never dropping old data, and teaching `merge()` about any new top-level key. A failed save is tracked in `engine.js` (`saveHealth`, `onSaveHealth`: `ok`, `idb-only` when localStorage fails but IndexedDB has it, `failing`, plus `stale` after a day without a good save) and shown as one quiet banner by `src/ui/savebanner.js`; `test/persistence.test.js` loads a saved state from every past schema (`test/fixtures/save-schema-*.json`; add one when you add a schema). Every copy (IndexedDB, cloud, sync file) is merged, not overwritten: practice time is kept per device in `state.hdev` and `history` is rebuilt from it; deletions leave a tombstone (`E.tombstone`). A merge is folded into the existing state objects (`patchInPlace` in `engine.js`; arrays are replaced), so an open tool that holds part of `E.state` (an exercise's tempo record, a skill's items) stays live across a sync or an import. Device-only settings (latency, mic) are listed in `DEVICE_SETTINGS`.
- Transcribe stores loaded audio in IndexedDB on the device only; song setups save with the rest of the state.
- Text from the player or another device (journal notes, song titles and links, routine names, anything in an imported backup or sync file) is only ever set with `h()`/`textContent`, never parsed as HTML; `innerHTML` is only cleared or set to a bundled SVG icon (`test/safety.test.js` checks this). Links from saved data are opened only if they are `http(s)`.
- Microphone input is opt-in. `src/listen.js` analyses it on the device (pitch, note onsets with exact timing); nothing is recorded or sent. Tools subscribe with `Mic.on(type, fn)` and the mic closes when the last listener unsubscribes. Every mic feature must also work by tapping.
